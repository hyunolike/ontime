# 온타임(OnTime) 설계

- 작성일: 2026-11-13
- 상태: 검토 대기
- 근거 자료: 온타임 기획서(접수양식 v2), 공모전 안내 페이지와 공지, Pleos 공식 문서. 확인한 사실은 [공모전 규정 요약](../../contest-rules.md)과 [Pleos SDK 확인 기록](../../pleos-sdk-notes.md)에 따로 정리했다.

기획서에 적힌 내용은 "기획서"로, 이 문서에서 새로 정한 내용은 "제안"으로 구분해 적는다.

## 1. 만드는 것과 이유

수속 마감이나 예약 시각처럼 놓치면 안 되는 시각을 등록해 두면, 주행 중에 마감까지 남는 여유를 분 단위 숫자 하나로 보여 주는 차량 앱이다. 여유가 줄어들면 더 가까운 주차장이나 충전 경유지를 하나만 말로 제안하고, 운전자가 수락하면 내비 경로를 바꾼다. 주차하고 내리면 남은 시간과 도보 안내가 스마트폰으로 이어진다.

운전자는 지금 내비, 항공사 앱, 캘린더를 번갈아 보며 머릿속으로 이 계산을 한다. 경로, 주행가능거리, 주차 시점이 입력 없이 모이는 곳이 차이므로 이 계산은 차가 대신하는 편이 정확하다.

이 설계의 직접 목표는 **12월 3~4일 최종 PT에서 Pleos Connect 에뮬레이터 위에 시나리오 A의 여섯 단계가 끊김 없이 동작하는 것**이다. 순위는 PT에서 시연한 결과물로 정해진다.

## 2. 목표와 범위

### 목표

1. 시나리오 A(전기차로 공항에 가는 가족, 16:40 출발편, 수속 마감 15:55)를 에뮬레이터에서 처음부터 끝까지 시연한다.
2. 심사 항목 "기술 활용성"에 맞게 다섯 SDK를 모두 핵심 흐름 안에서 쓴다.
3. 네트워크가 끊기거나 차량 값이 지원되지 않아도 시연이 멈추지 않는다.
4. 여유 숫자가 어떻게 나왔는지 항목별로 설명할 수 있다.

### 시연할 시나리오 A

기획서의 여섯 단계다. 숫자는 기획서의 값이다.

| 단계 | 상황 | 앱이 하는 일 | 여유 |
|---|---|---|---|
| ① 전날 밤 | 정차 중 음성으로 항공편 등록 | 수속 마감 기준으로 "내일 14:30까지 출발하면 여유 30분입니다" | +30분 |
| ② 당일 출발 | 앱 실행 | 목적지를 공항 주차장으로 설정 | +28분 |
| ③ 고속도로 | 사고 정체 | "단기주차장으로 바꾸면 12분을 아낄 수 있습니다", "그렇게 해 줘", 목적지 변경 | +9분에서 +21분 |
| ④ 주행 중 | 배터리가 넉넉하지 않음 | "도착은 가능합니다. 돌아오는 길을 위해 공항 주차장 충전기를 이용하세요" | 유지 |
| ⑤ 주행 중 | 항공편 지연 수신 | 지연 사실을 알리되 마감은 그대로 둔다 (11절) | 유지 |
| ⑥ 도착 | 주차 후 하차 | 스마트폰에 마감까지 남은 시간과 도보 소요 표시 | 폰으로 이동 |

### 하지 않는 것

- 열차, 병원, 공연 일정과 캘린더 자동 인식 (기획서의 2단계 이후)
- 인천공항 외의 공항
- 주차 예약, 충전 예약, 결제
- 계정 가입과 로그인. 기기 하나에 일정 하나만 다룬다
- 실차 검증

### 이렇게 되면 실패다

- 여유 숫자가 근거 없이 낙관적으로 나온다. 항공편이 지연됐다는 소식만으로 마감을 늦추지 않는다.
- 주행 중에 운전자가 화면을 만져야 한다.
- 같은 상태에서 음성 안내가 반복되거나, 임계값 근처에서 상태가 오락가락해 안내가 연달아 나온다.
- 재생한 데이터를 실제 데이터인 것처럼 보여 준다.

## 3. 기획서와 달라지는 점

공모전 규정과 공식 문서를 대조해 보니 기획서 그대로는 만들 수 없는 부분이 있었다.

| 기획서 | 확인한 사실 | 설계에서의 처리 |
|---|---|---|
| 음성 등록과 대안 수락을 Gleo Interface 기능으로 등록 | 공지에 공모전 참가팀은 Gleo Interface 검토와 승인을 신청할 수 없다고 명시돼 있다 | SpeechToText로 발화를 텍스트로 받고 앱 안에서 직접 해석한다 (5.4절) |
| 도착 예정 시각을 내비 리스너로 받는다 | 문서에 콜백 이름만 있고 남은 시간 필드 설명이 없다 | 첫 번째 PoC로 확인한다. 못 받으면 서버가 경로 소요 시간을 계산한다 (7절) |
| 기어 P 전환으로 주차를 감지 | Vehicle 도메인 목록에 기어가 없다. 에뮬레이터에는 기어 값이 있다 | PoC로 getter를 찾는다. 없으면 목적지 도착 이벤트와 도어 열림으로 판단한다 |
| 하차 후 "B2 14구역" 표시 | 차량 신호만으로는 주차 구역을 알 수 없다 | 주차장 이름까지만 자동으로 넣고, 층과 구역은 정차 후 말이나 터치로 입력한 경우에만 표시한다 |
| 11/16부터 개발 시작 | 저장소와 APK는 11/15 접수 때 함께 내야 가산점 대상이다 | 4절의 0단계로 접수 전 최소 동작본을 둘지 결정이 필요하다 |

**접수 전에 기획서 5번(개발 계획)의 Gleo Interface 서술은 SpeechToText 기반으로 고쳐야 한다.** 공지에서 쓸 수 없다고 밝힌 기능을 개발 계획에 적으면 기술 활용성 항목에서 감점 요인이 된다.

## 4. 접근 방식

세 가지를 검토했다.

**A. 차량 앱 단독.** 공공 API를 앱이 직접 부르고 서버를 두지 않는다. 가장 빨리 만들 수 있지만 개발계정 호출 한도(운항 하루 500건)를 차량마다 쓰게 되고, 서비스 키가 APK에 들어가며, 하차 후 스마트폰으로 넘길 방법이 없다.

**B. 차량 앱과 서버, 모바일 웹을 한 저장소에 둔다 (선택).** 계산은 차량 앱이 하고, 서버는 운항과 주차 정보를 모아 두는 역할과 하차 정보를 스마트폰에 전달하는 역할만 맡는다. 기획서의 구성과 같고, 서버가 죽어도 차량 앱은 마지막 값으로 계속 동작한다.

**C. 서버가 계산까지 한다.** 차량 앱은 화면만 그린다. 계산 로직을 고치기는 쉽지만 통신이 끊기면 숫자가 멈춘다. 터널과 지하 주차장이 시나리오의 일부라서 맞지 않는다.

B를 고른 이유는 기획서가 이미 이 구성을 전제하고 있고, 통신 단절에 견디며, 호출 한도 문제를 서버 한 곳에서 관리할 수 있어서다.

B 안에서 한 가지를 더 정했다. **Pleos SDK를 쓰는 부분은 모두 인터페이스 뒤에 두고, 실제 구현과 재생용 가짜 구현을 함께 만든다.** 문서로 확인하지 못한 API가 여럿이라 실제 구현이 막혀도 나머지 개발이 멈추지 않아야 하고, PT 현장에서 에뮬레이터 값 주입이 실패했을 때 대신 쓸 수단도 필요하다.

### 5.1 여유 시간 계산 (`core-slack`)

Android에 의존하지 않는 순수 Kotlin 모듈로 둔다. 시연의 신뢰도가 이 숫자에 달려 있어 단위 테스트로 촘촘히 검증하기 위해서다.

```
여유(분) = 유효 마감 − 현재 시각 − 남은 주행 시간 − 주차 소요 − 도보 소요 − 경유지 정차 − 안전 버퍼
```

- **유효 마감**: 사용자가 등록한 마감, 또는 운항 API에서 해당 편의 마감 변경이 확인된 값. 출발 지연만으로는 바꾸지 않는다.
- **남은 주행 시간**: 현재 위치에서 주차장 입구까지. 주차장 안 이동은 주차 소요에 넣어 중복으로 빼지 않는다.
- **주차 소요와 도보 소요**: 주차장별 기준표에서 가져온다. 인천공항 T1과 T2의 단기, 장기 주차장만 만든다.
- **표시 값은 내림한다.** 8.9분은 +8분으로 보여 준다. 상태 판정은 반올림 전 값으로 한다.

입력마다 값, 받은 시각, 출처(실제, 캐시, 재생)를 함께 들고 다닌다. 출처가 재생이면 화면에 표시하고, 주행 시간 입력이 일정 시간 이상 오래되면 숫자 옆에 받은 시각을 붙이고 대안 제안을 멈춘다.

상태는 기획서의 기준을 따른다.

| 상태 | 진입 기준 | 화면 | 음성 |
|---|---|---|---|
| 여유 | +15분 이상 | 초록 숫자 | 없음 |
| 주의 | +5분 이상 +15분 미만 | 주황 숫자 | 상태가 바뀔 때 한 번 |
| 위험 | +5분 미만 | 빨간 숫자 | 대안 하나를 제안하고 답을 듣는다 |

제안: 상태가 좋아지는 방향으로 넘어갈 때는 기준보다 2분 더 여유가 있어야 바뀌게 한다. 14분과 15분 사이를 오가며 안내가 반복되는 일을 막기 위해서다. 버퍼와 기준값은 일정 종류별 설정으로 빼 둔다.

### 5.2 대안 선택

위험 상태가 되거나 주행가능거리가 부족할 때 대안 후보를 만들고 하나만 고른다.

- **주차장 변경**: 같은 터미널의 다른 주차장으로 목적지를 바꿨을 때의 여유를 다시 계산한다. 서버가 주는 주차장 혼잡도를 반영한다.
- **충전 경유**: 주행가능거리가 목적지까지의 거리보다 부족할 때만 경로 위 충전소 하나를 경유지로 넣는다. 도착은 가능하고 돌아오는 길만 부족하면 경유 없이 공항 주차장 충전기를 안내한다.
- 고른 대안이 여유를 3분 이상 늘리지 못하면 제안하지 않는다 (제안, 설정값).
- 수락하면 `requestRoute()`나 `addWaypoint()`를 부르고, `onRoutingCompleted()`를 받은 뒤에 새 여유를 말한다. 거절하거나 답이 없으면 경로를 유지하고 같은 대안은 다시 꺼내지 않는다.

### 5.3 차량 플랫폼 계층

`platform-api`에 네 인터페이스를 둔다.

| 인터페이스 | 주는 것 | Pleos 구현 | 막혔을 때 |
|---|---|---|---|
| `NaviGateway` | 남은 주행 시간, 목적지, 경로 이벤트. 목적지 변경과 경유지 추가 | NaviHelper | 서버의 경로 소요 시간 계산 |
| `VehicleGateway` | 주행가능거리, 주행 여부, 도어 열림 | Vehicle | 지원되지 않는 값에 묶인 기능만 끈다 |
| `SpeechGateway` | 말하기, 한 번 듣기 | TextToSpeech, SpeechToText | 정차 중 터치 입력 |
| `LocationGateway` | 현재 위치 | FusedLocation | Android 표준 위치 API |

값은 모두 Kotlin Flow로 내보낸다. 각 구현은 시작할 때 지원 여부(`checkXxxCapabilities`, `isSupported()`)를 확인해 결과를 함께 알려 주고, 앱은 지원되지 않는 값에 기대는 기능을 화면에서 뺀다.

`platform-fake`는 시나리오 파일(JSON, 시각별 입력값)을 읽어 같은 인터페이스로 재생한다. 빌드 종류(flavor)를 `pleos`와 `fake`로 나눠, `fake`는 Pleos 이미지가 없는 일반 에뮬레이터에서도 돌아가게 한다. 제출하는 APK는 `pleos`다.

### 5.4 음성 (`core-voice`)

Gleo Interface를 쓸 수 없으므로 SpeechToText가 돌려준 문장을 앱이 직접 해석한다. LLM 없이 규칙으로 처리한다.

- **일정 등록** (정차 중에만): "내일 4시 40분 제주행 비행기 등록해 줘"에서 날짜, 시각, 행선지나 편명을 뽑는다. 뽑은 값으로 서버에 운항편을 조회해 후보가 하나면 확인 문장을 말하고, 여럿이면 되묻는다. 인식에 실패하면 터치 입력 화면을 연다.
- **대안 수락** (주행 중): 앱이 제안을 말한 직후에만 한 번 듣는다. "그렇게 해 줘", "응", "바꿔 줘"는 수락으로, "아니", "괜찮아"와 무응답은 거절로 본다. 애매하면 거절로 처리한다.

주행 중에는 앱이 먼저 말을 걸었을 때만 마이크를 연다. 듣는 시간은 짧게 제한한다.

### 5.5 화면

| 화면 | 언제 | 내용 |
|---|---|---|
| 주행 화면 | 주행 중 | 여유 숫자와 색, 마감 시각, 목적지 이름. 버튼 없음 |
| 제안 띠 | 위험 상태에서 대안이 있을 때 | 주행 화면 아래에 제안 문장 한 줄. 음성으로만 답한다 |
| 정차 화면 | 주행하지 않을 때 | 주행, 주차, 도보 내역과 일정 등록, 설정 |
| 하차 화면 | 스마트폰 | 마감까지 남은 시간, 주차장, 도보 소요 |

주행 여부는 `VehicleGateway`가 알려 준다. 기어 값을 못 받으면 내비의 주행 상태와 속도로 판단한다. 세로형 12.9인치와 가로형 14.6인치 두 폼팩터에서 깨지지 않게 만든다.

### 5.6 서버

Spring Boot와 Kotlin으로 만든다. 저장소는 H2 하나로 충분하다.

- **수집**: 등록된 항공편과 그 터미널의 주차장만 주기적으로 조회해 저장한다. 하루 호출 수는 `조회 대상 수 × 갱신 횟수`로 미리 계산해 한도(운항 500건, T1 주차 1,000건) 안에서 주기를 정한다.
- **차량 앱용 API**: 일정 등록과 조회, 운항편 검색, 주차장 현황, 경로 소요 시간(보완용). 차량 앱은 30초에서 1분 간격으로 조회한다. 응답마다 원본 데이터를 받은 시각을 넣는다.
- **하차 전달**: 차량 앱이 하차를 알리면 서버가 저장하고, 미리 연결해 둔 스마트폰의 모바일 웹이 이를 받아 표시한다. 연결은 정차 화면의 QR 코드를 스마트폰으로 찍어서 한다. 로그인은 없고 QR에 담긴 임의 토큰으로 구분한다.
- **재생 모드**: 서비스 키 없이도 저장해 둔 응답으로 동작한다. 심사위원이 저장소를 받아 바로 실행할 수 있어야 하고, PT 현장의 네트워크를 믿을 수 없기 때문이다.

제안: T1 주차면 API는 단기주차장만 제공한다고 알려져 있어, 장기주차장은 한국공항공사나 인천공항의 다른 주차 API를 실제로 호출해 본 뒤 범위를 정한다. 확보하지 못하면 기준표의 고정값을 쓰고 화면에 그렇게 표시한다.

### 5.7 오류 처리

| 상황 | 동작 |
|---|---|
| 서버 연결 끊김 | 마지막 값으로 계속 계산한다. 주행 시간은 차에서 오므로 숫자는 계속 움직인다 |
| 주행 시간 입력이 끊김 | 숫자 옆에 받은 시각을 표시하고 대안 제안을 멈춘다 |
| 경로 요청 실패 (`onError`) | "경로를 바꾸지 못했습니다"라고 한 번 말하고 기존 경로와 숫자를 유지한다 |
| 차량 값 미지원 | 해당 기능을 끄고 정차 화면에 지원 범위를 표시한다 |
| 음성 인식 실패 | 주행 중이면 거절로 처리하고, 정차 중이면 터치 입력으로 넘긴다 |
| 이미 마감을 지킬 수 없음 | 숫자를 음수로 보여 주고 서두르라는 안내는 하지 않는다. 정차 후 항공사 연락을 권한다 |

### 5.8 테스트

- `core-slack`과 `core-voice`는 단위 테스트를 먼저 쓰고 구현한다. 기획서의 +28, +9, +21분 장면을 그대로 테스트 케이스로 옮긴다.
- 시나리오 A 전체는 `platform-fake`로 재생하는 통합 테스트로 검증한다.
- Pleos 구현은 자동 테스트 대신 에뮬레이터에서 요청과 응답 로그를 남겨 `docs/pleos-sdk-notes.md`의 상태를 "에뮬레이터 검증"으로 바꾼다. 이 로그는 PT 자료로도 쓴다.
- 서버는 재생 모드 응답을 기준으로 API 테스트를 둔다.

## 6. 개발 환경

확인한 현재 상태와 준비할 것이다.

| 항목 | 현재 | 할 일 |
|---|---|---|
| Android Studio와 Android SDK | 설치돼 있지 않다 | 설치 후 Pleos 시스템 이미지(Mac용 arm64) 추가 |
| JDK | 11, 17, 21, 25 설치됨 | 차량 앱은 17, 서버는 21 |
| Gradle | 9.8.1 | 프로젝트마다 Gradle 8.x wrapper를 따로 둔다. 공모전 요건은 8.0 이상이다 |
| Go 1.22 이상 | 미확인 | 폼팩터 테스트 도구에 필요 |
| Pleos Playground My Project | 미확인 | STT와 TTS의 서버 모드에 Client ID와 Secret이 필요하다 |
| 공공데이터포털 서비스 키 | 미확인 | 운항 현황, 주차 현황 활용 신청 |

차량 앱은 minSdk 28, compileSdk와 targetSdk 34로 맞춘다. 비밀값은 저장소에 넣지 않고 `local.properties`와 `.env`로 주입한다. 저장소는 11월 16일에 공개로 전환해야 하므로 처음부터 개인정보와 키가 들어가지 않게 관리한다.

## 7. 먼저 확인할 것 (PoC)

문서로 확인하지 못한 항목이다. 구현 전에 에뮬레이터에서 순서대로 확인하고, 결과에 따라 범위를 조정한다.

| 순서 | 확인할 것 | 실패하면 |
|---|---|---|
| 1 | Apple Silicon Mac에서 Pleos 에뮬레이터가 뜨고 Virtual Console이 동작하는가 | 다른 장비를 구하거나 `fake` 빌드와 녹화 영상으로 시연을 준비한다. 가장 큰 위험이다 |
| 2 | NaviHelper로 남은 주행 시간을 받는가 (`onTripInfo`, `onRouteStateInfo`, `onDrivingInfo`) | 서버가 외부 길찾기 API로 소요 시간을 계산한다. 공급자는 그때 정한다 |
| 3 | `requestRoute()`로 주행 중 목적지가 실제로 바뀌는가, 에뮬레이터 내비에 경로를 어떻게 만드는가 | 목적지 변경을 내비 화면 요청으로 대체할 수 있는지 본다 |
| 4 | 기어 상태와 주행가능거리 getter | 5.3절의 대체 판단을 쓴다 |
| 5 | STT가 한국어 자유 발화를 받는가, `ON_DEVICE`로 되는가 | 서버 모드로 앱 등록을 하거나 수락 표현을 짧은 단어로 좁힌다 |
| 6 | 공공 API 실제 응답 (운항 현황, 주차 현황) | 재생 모드 데이터로 시연하고 화면에 표시한다 |

## 10. 시연 구성과 세부 결정

설계 검토에서 나온 질문에 대한 답이다. 모두 제안이며 바꿀 수 있다.

**시간과 교통은 시연용으로 재생한다.** 서 있는 에뮬레이터에서는 하루에 걸친 시나리오와 사고 정체를 만들 수 없다. 그래서 `pleos` 빌드에서도 입력별로 출처를 고를 수 있게 한다. 시연에서는 현재 시각과 남은 주행 시간을 시나리오 파일로 흘리고, 목적지 변경, 차량 값, 음성은 실제 SDK를 쓴다. 재생 중인 입력이 있으면 화면 구석에 "시연 재생" 표시를 항상 띄우고, PT에서도 어느 부분이 재생인지 먼저 밝힌다. 정차 화면에 시연 조작판(다음 장면으로, 정체 발생, 지연 수신)을 둔다.

**마감은 출발 예정 시각에서 정해 둔 시간을 빼서 구한다.** 일정 종류별 기본값(국제선은 출발 60분 전)을 쓰고, 등록할 때 "수속 마감 15시 40분으로 등록할까요"라고 확인받는다. 운항 API에는 수속 마감 필드가 없으므로 마감은 사용자가 다시 확인했을 때만 바뀐다. 그래서 시나리오 ⑤는 기획서와 달리 "출발이 20분 지연됐습니다. 수속 마감은 그대로 15시 40분으로 계산합니다"라고 알리는 데서 끝나고, 휴게소 안내는 넣지 않는다.

**시연 항공편은 인천 출발 실제 편으로 바꾼다.** 기획서의 예시는 제주행인데, 제주행 국내선은 대부분 김포에서 뜨고 이 설계의 범위는 인천공항이다. 운항 API를 실제로 호출해 본 뒤 오후 출발 국제선 하나를 골라 그 응답을 재생 데이터로 고정한다. 장면별 여유 숫자(+30, +28, +9, +21)는 유지하고 시각만 그 편에 맞춘다.

**출발 시각 안내 때문에 서버의 경로 소요 시간 계산은 필수다.** 단계 ①은 주행 전이라 내비에서 값을 받을 수 없다. PoC 2번 결과와 무관하게 서버에 외부 길찾기 API 연동을 둔다. 공급자는 무료 한도와 교통 반영 여부를 보고 1단계에서 정한다.

**앱은 손으로 실행한다.** 시동 시 자동 실행은 문서에서 방법을 확인하지 못했다. 시연에서는 앱을 직접 열고, 열리면 등록된 일정의 목적지를 자동으로 설정한다.

**충전 경유는 판단까지를 필수로, 경유지 추가는 여유가 되면 한다.** 시나리오 ④의 결론은 멈출 필요가 없다는 것이므로 주행가능거리와 남은 거리를 비교하는 판단이 핵심이다. `addWaypoint()`로 충전소를 넣는 흐름은 시연 경로 위 충전소 두세 곳을 고정 목록으로 두고 2단계 끝에 시간이 남으면 넣는다.

**PT에서 서버는 시연 노트북에서 돌린다.** 에뮬레이터는 `10.0.2.2`로 접속하고, 스마트폰은 휴대폰 핫스팟으로 노트북과 같은 망에 둔다. QR에 담는 주소는 설정값으로 뺀다. 핫스팟도 안 될 때를 대비해 하차 화면은 예비 영상을 준비한다.

**안전 버퍼의 초깃값은 3분이다.** 검증된 값은 아니고 설정으로 바꿀 수 있다. 하차 후에는 `마감까지 남은 시간 − 도보 − 버퍼`로 계산한다. 화면 시안의 숫자를 테스트로 옮길 때는 버퍼를 포함해 같은 여유가 나오도록 현재 시각을 맞춘다. 시안 3의 "26분"은 여유가 아니라 마감까지 남은 시간으로 표시한다.

## 11. 본인이 직접 준비해야 하는 것

신청하고 승인받는 데 시간이 걸릴 수 있어 먼저 해 두면 좋다. 늦어지면 재생 모드를 먼저 만들고 PoC 5번과 6번을 뒤로 미룬다.

- Pleos Playground 가입과 My Project 생성 (Client ID, Client Secret)
- 공공데이터포털에서 인천국제공항공사 운항 현황과 주차 현황 API 활용 신청
- Android Studio 설치

## 12. 이 문서에서 내가 정한 것

기획서에 없던 결정이다. 검토하면서 바꿔도 된다.

1. 서버도 Kotlin으로 쓴다. 차량 앱과 언어를 맞춰 혼자 개발할 때 전환 부담을 줄이려는 것이다. Java가 더 익숙하면 바꾼다.
2. 서버 저장소는 H2다. 시연 규모에 별도 DB는 과하다.
3. 스마트폰 연결은 QR 코드와 임의 토큰으로 한다.
4. 음성 해석은 규칙 기반이다.
5. 상태 전환에 2분의 완충을 두고, 여유를 3분 이상 늘리지 못하는 대안은 제안하지 않는다.
6. 로컬 폴더와 저장소 이름은 `ontime`이다.
7. 10절의 결정 전부. 특히 시연 항공편을 인천 출발편으로 바꾸는 것과 시나리오 ⑤에서 휴게소 안내를 빼는 것은 기획서 내용과 달라진다.
